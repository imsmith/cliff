Cliff

A literate walkthrough of a containerized development environment for elastic infrastructure work

Cliff gets you up close to the cloud without forcing you to learn to fly.

—the project tagline, said unironically

Working with elastic infrastructure is, among other things, an exercise in toolchain accumulation. Terraform pins itself to a version that disagrees with your provider plugin. kubectl minor-version skew breaks kubectl explain. The Google Cloud SDK upgrades itself in the background and now your CI script writes a different lockfile than your laptop. Three cloud CLIs, half a dozen provider CLIs, two language runtimes, an observability binary you used once and forgot to uninstall — and the host operating system is silently the place all of them have agreed to fight in.The host is the wrong place for cloud tooling for the same reason the host is the wrong place for production binaries: nothing about it was designed for the workload, and the cost of being wrong about that is paid one mysterious 3 a.m. terraform apply at a time.

Cliff is the wager that this is solvable by putting the entire toolchain into a small set of container images, layering them so the substrate is shared, and entering them through a host-side launcher that knows how to scope credentials, restrict egress, and write down what happened. The four images are the substrate. The launcher is the discipline. This document walks both, in roughly the order a new user encounters them.

0. Why four images, not one

The naive build is one fat image with everything in it: Elixir, Tcl, Terraform, kubectl, Prometheus, Grafana, the cloud CLIs, all of it. Pulled once, available everywhere, no decisions for the user. It is also six gigabytes, takes ten minutes to build, and forces every container session to inherit every dependency some other unrelated tool dragged in. Cliff splits the work along a different seam.

The split: a base image with shell quality-of-life, the project's language runtimes, and a non-root user; a dev image that adds the infrastructure-as-code stack and the cloud provider CLIs; an obsv image that adds the monitoring and logging binaries; and a full image that combines dev and obsv for sessions where the separation isn't worth the build time. Each image is FROM the previous, so the layer cache is shared and pulls are incremental.A practical consequence: you almost never want to docker pull cliff-full on a fresh machine. Pull cliff-dev, do your work, and only fetch the obsv layers if you actually need to query a Prometheus.

The split is a claim about how the work decomposes. Most sessions are either "I am writing infrastructure code" or "I am chasing a problem through telemetry." The first wants Terraform and a cloud CLI; the second wants Loki and a Grafana. They want different things badly enough to justify two images. They want enough shared things — a shell, a language runtime, a CA bundle — to justify a base.

1. The base image

Every cliff container starts here. The base image is Alpine 3.23, chosen for its small package surface and its musl-libc footprint, plus a curated set of tools that any session will want regardless of what it's doing.

FROM alpine:3.23

ENV LANG=C.UTF-8

RUN apk add --no-cache \
    bash curl wget git jq yq tmux mosh fish sudo shadow \
    openssh-client wireguard-tools sqlite ca-certificates \
    build-base openssl openssl-dev ncurses-dev libstdc++ \
    unzip tar gzip xz coreutils

Three groups in one apk add: the quality-of-life shell stack (bash, fish, tmux, mosh), the data-shoveling utilities (curl, jq, yq, sqlite), and the build dependencies (build-base, the -dev packages, libstdc++) that exist so Erlang and Elixir can compile NIFs at install time.The build-base meta-package costs about 200 MB of image size; the alternative is to ship without NIF support and discover at runtime that Elixir can't load :crypto. The trade is worth making once, at build time, where it's invisible to the session. wireguard-tools is in the base because cliff sessions sometimes need to reach a private network; mosh because they sometimes need to survive a flaky one.

The next two lines are unobtrusive but load-bearing:

COPY images/ca/cliff-egress.crt /usr/local/share/ca-certificates/cliff-egress.crt
RUN update-ca-certificates

This bakes the cliff-egress mitmproxy CA into the system trust store. The CLI runs a per-session mitmproxy sidecar to enforce the egress allowlist (covered later); without the CA in the trust store, every TLS connection from the container would fail certificate validation, and every terraform init would erupt into x509 errors. Building the CA into the image instead of bind-mounting it at runtime keeps the per-session setup trivial and means an image-only user (no CLI) can still reach the public internet without surprises.

RUN apk add --no-cache tcl tk
RUN apk add --no-cache erlang erlang-dev elixir

The two language runtimes the project itself is written in. Tcl is the scripting language for cliff's profiles and the launcher. Elixir is the application language for the wider ecosystem cliff supports. Putting them in the base image — rather than a language-specific layer — is a deliberate choice: any cliff session might want to run a Tcl helper, any session might want to drop into iex. Specialization belongs upstream of the runtime, not downstream of it.

RUN adduser -D -s /usr/bin/fish devuser && \
    echo "devuser ALL=(ALL) NOPASSWD: ALL" >> /etc/sudoers
RUN chsh -s /usr/bin/fish devuser 2>/dev/null || true

RUN mkdir -m 0755 /nix && chown devuser:devuser /nix
USER devuser
WORKDIR /home/devuser

RUN curl -L https://nixos.org/nix/install | sh -s -- --no-daemon && \
    echo '. ~/.nix-profile/etc/profile.d/nix.sh' >> ~/.bashrc || true

RUN mix local.hex --force && mix local.rebar --force

CMD ["/usr/bin/fish"]

The user, the shell, and the escape hatch. devuser is the unprivileged identity every session runs as; passwordless sudo exists because installing things inside an interactive container session is a normal thing to want to do, and locking it down would just make people fight the container."But sudo!" — yes, this is a defense-in-depth story. The container is ephemeral by default, the user is unprivileged at the kernel layer, the egress is allowlisted, and the workspace mount is configurable. Passwordless sudo inside the container is a productivity affordance, not a security boundary. Nix is installed single-user under devuser so the session has a way to install something the image didn't think of, without sudo and without polluting /usr. mix local.hex and mix local.rebar save the session from a "where's hex?" question every time someone runs an Elixir build.

2. The dev image

The dev image adds the IaC and provider-CLI stack on top of base. Each tool's install method is whatever its upstream considers official, which is a less coherent story than one might want and a more honest one than the alternative.

FROM ghcr.io/imsmith/cliff-base:0.3.0

USER root

RUN TERRAFORM_VERSION="1.14.5" && \
    curl -fsSL "https://releases.hashicorp.com/terraform/${TERRAFORM_VERSION}/terraform_${TERRAFORM_VERSION}_linux_amd64.zip" -o /tmp/terraform.zip && \
    unzip /tmp/terraform.zip -d /usr/local/bin/ && \
    rm /tmp/terraform.zip

RUN VAULT_VERSION="1.21.2" && \
    curl -fsSL "https://github.com/hashicorp/vault/archive/refs/tags/v${VAULT_VERSION}.zip" -o /tmp/vault.zip && \
    unzip /tmp/vault.zip -d /usr/local/bin/ && \
    rm /tmp/vault.zip

RUN PACKER_VERSION="1.15.0" && \
    curl -fsSL "https://github.com/hashicorp/packer/archive/refs/tags/v${PACKER_VERSION}.zip" -o /tmp/packer.zip && \
    unzip /tmp/packer.zip -d /usr/local/bin/ && \
    rm /tmp/packer.zip

RUN KUBECTL_VERSION="v1.35.1" && \
    curl -fsSL "https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/linux/amd64/kubectl" -o /usr/local/bin/kubectl && \
    chmod +x /usr/local/bin/kubectl

RUN curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

The HashiCorp tools and kubectl get pinned versions, fetched from upstream as zips, unpacked into /usr/local/bin. Helm uses its official install script, which is unpinned — this is a small wart; bumping cliff's version forces a rebuild that picks up whatever Helm has shipped since.Pinning Helm explicitly would mean reading the install script and reproducing what it does. The trade-off was made in favor of using the upstream-blessed path; the cost is that "the same tag of cliff-dev, built on a different day, has a different Helm" is technically true. Acceptable for a developer environment, not acceptable for a release artifact.

RUN apk add --no-cache python3 py3-pip && \
    pip3 install --break-system-packages ansible-core

RUN apk add --no-cache aws-cli || \
    (pip3 install --break-system-packages awscli)

RUN pip3 install --break-system-packages azure-cli 2>/dev/null || \
    echo "Azure CLI install skipped (may need manual install)"

The Python-installed tools. Ansible is pip-installed because Alpine's apk-packaged version lags behind upstream by a release or two. AWS CLI prefers the apk package and falls back to pip when the apk package is unavailable — it has been intermittently missing from Alpine's community repository, and the fallback pattern survives that without breaking the build. Azure CLI is the worst offender: it routinely fails to install on Alpine because of native dependencies that don't quite work under musl, so the build emits a warning and continues rather than failing. A session that needs Azure CLI is on notice.There is a path through this: build Azure CLI in a multi-stage image with glibc compatibility shims. It is on the list. It is not at the top of the list.

RUN curl -fsSL https://dl.google.com/dl/cloudsdk/channels/rapid/downloads/google-cloud-cli-linux-x86_64.tar.gz -o /tmp/gcloud.tar.gz && \
    tar -xzf /tmp/gcloud.tar.gz -C /opt/ && \
    /opt/google-cloud-sdk/install.sh --quiet --path-update=true && \
    ln -sf /opt/google-cloud-sdk/bin/gcloud /usr/local/bin/gcloud && \
    rm /tmp/gcloud.tar.gz

RUN apk add --no-cache tailscale || \
    (curl -fsSL https://pkgs.tailscale.com/stable/tailscale_latest_amd64.tgz -o /tmp/tailscale.tgz && \
     tar -xzf /tmp/tailscale.tgz -C /tmp/ && \
     cp /tmp/tailscale_*/tailscale /usr/local/bin/ && \
     rm -rf /tmp/tailscale*)

RUN apk add --no-cache nodejs npm && \
    npm install -g wrangler

RUN STEP_VERSION="0.29.0" && \
    curl -fsSL "https://dl.smallstep.com/gh-release/cli/gh-release-header/v${STEP_VERSION}/step_linux_${STEP_VERSION}_amd64.tar.gz" -o /tmp/step.tar.gz && \
    tar -xzf /tmp/step.tar.gz -C /tmp/ && \
    cp /tmp/step_*/bin/step /usr/local/bin/ && \
    rm -rf /tmp/step*

USER devuser

The remaining tools follow the same pattern with minor variations: Google Cloud SDK from upstream tarball; Tailscale from apk with tarball fallback; Cloudflare's Wrangler dragged in via npm (and Node.js along with it); Smallstep's step CLI from upstream. Three things are worth naming. First, the dev image now contains three language runtimes — Elixir from base, Python from Ansible, Node from Wrangler — none of which the session asked for, all of which are baggage some tool requires. Second, every install path is different, because every upstream made different choices, and pretending otherwise would just hide the breakage. Third, the image returns to USER devuser at the end so the running container is unprivileged by default.

3. The obsv image

The obsv image is the telemetry exploration tier. It is not a monitoring stack — cliff is a development environment, not a place to run production Prometheus. It contains the binaries you want when you are looking at someone else's running stack: promtool against an existing Prometheus, logcli against an existing Loki, an ad-hoc Grafana for staring at metrics, a Vector you can experiment with, an osquery for poking at the host you've SSHed to, a psql for everything that ended up in Postgres.

FROM ghcr.io/imsmith/cliff-base:0.3.0

RUN PROM_VERSION="3.9.1" && \
    curl -fsSL ".../prometheus-${PROM_VERSION}.linux-amd64.tar.gz" -o /tmp/prometheus.tar.gz && \
    tar -xzf /tmp/prometheus.tar.gz -C /tmp/ && \
    cp /tmp/prometheus-*/prometheus /usr/local/bin/ && \
    cp /tmp/prometheus-*/promtool /usr/local/bin/

RUN GRAFANA_VERSION="12.3.3" && curl -fsSL "..." -o /tmp/grafana.tar.gz && tar ...
RUN LOKI_VERSION="3.6.6" && curl -fsSL "..." && unzip ...
RUN VECTOR_VERSION="0.53.0" && curl -fsSL "..." && tar ...

RUN apk add --no-cache osquery 2>/dev/null || \
    (OSQUERY_VERSION="5.21.0" && \
     curl -fsSL "..." -o /tmp/osquery.deb && \
     ar x /tmp/osquery.deb && tar -xzf data.tar.gz -C / 2>/dev/null || \
     tar -xf data.tar.zst -C / 2>/dev/null)

RUN apk add --no-cache postgresql-client

The pattern is by now familiar — pinned versions, upstream release tarballs, unpacked into /usr/local/bin. The osquery install is the ugliest because osquery does not ship Alpine packages and the maintainers have so far declined to; the fallback unpacks the Debian .deb into the Alpine root with a tar invocation that handles two compression formats, because the deb has switched between gzip and zstd at least once in living memory.This is the worst install path in the repository. It works. It is not pretty. The alternative — building osquery from source — is a multi-hour CI job. The trade was made in favor of "works most of the time, fails loudly when it doesn't."

What's not in obsv is as load-bearing as what is. There is no Alertmanager, because cliff is not where you handle alerts. No Tempo, because tracing is the dev image's problem if it's anyone's. No exporters — node_exporter, blackbox_exporter — because cliff is the consumer, not the producer. The discipline is "tools to look at telemetry," not "a stack to generate it."

4. The full image

Cliff-full is, structurally, cliff-dev with the obsv RUN blocks layered on top. It is not built FROM cliff-obsv-and-cliff-dev (Docker has no such operation); it is built FROM cliff-dev with the obsv install steps repeated. This is duplication of source, not duplication of layers — the resulting image shares all of dev's layers with cliff-dev, and adds new layers for the obsv tools. A user who pulls both cliff-dev and cliff-full pays for the obsv layers exactly once.

The duplication of source is real, and it is a wart. If the obsv install steps change, both Dockerfile.obsv and Dockerfile.full have to be updated. The alternative — extracting the obsv steps into a script that both Dockerfiles call — was considered and rejected on the grounds that "two short Dockerfiles you can read" beats "one Dockerfile and a script you have to chase." If the divergence ever exceeds three RUN blocks, the calculus changes.

Cliff-full exists for the case where the separation between dev and obsv isn't worth a session boundary. Diagnosing a deployment problem often means writing terraform and reading metrics in the same shell history. Two containers, two terminal tabs, one head: cliff-full is the answer when the head is the bottleneck.

5. The launcher

Docker-compose is fine for "give me a shell." It is not fine for "let an LLM run terraform here." The difference is everything cliff's launcher does between docker run and the prompt: minting a scoped credential, spinning up a per-session egress proxy, mounting a tmpfs at /run/creds, capping CPU and memory and PIDs, recording what happened, and tearing it all down on exit.

The launcher is bin/cliff, four lines of Tcl that load the rest of the implementation and dispatch a subcommand:

#!/usr/bin/env tclsh
set ::CLIFF_ROOT [file normalize [file join [file dirname [info script]] ..]]
source [file join $::CLIFF_ROOT lib cliff main.tcl]
::cliff::main::dispatch $argv

The subcommands are list, describe, run, exec, sessions, and session. list shows the available profiles. describe <profile> shows the resolved profile after inheritance. run launches an interactive shell. exec launches a one-shot command and returns its exit code. sessions lists recent sessions. session <id> shows the detail of one.

5.1 Profiles

A profile declares a session's posture: which image, how the workspace is mounted, what the home directory is, what credentials to mint, what egress to allow, what resource caps to apply. Profiles are written in Tcl, with a small DSL that the launcher evaluates in a sandboxed interpreter.Tcl was chosen because the project already standardizes on it for scripting, the syntax is forgiving (no quoting wars over JSON commas), and a profile DSL is exactly what Tcl is good at: a small set of commands that read like configuration. The floor profile is base.tcl:

describe "Floor profile: tmpfs home, no creds, no egress"
image    cliff-base:0.3.0

workspace mode=ro
home      mode=tmpfs size=256m

limits { cpus 1; memory 1g; pids 256 }

The discipline is in what isn't there. No creds block, so no credentials. No egress block, so no outbound network. The workspace is read-only. The home directory is a 256 MB tmpfs that vanishes when the container exits. CPU and memory and PID counts are capped low. A session in the base profile can read your code and run scripts; it cannot reach the network, cannot write to disk except in the tmpfs, and cannot exhaust the host.

Richer profiles inherit from base and add affordances:

inherit base
describe "Dev image, writable workspace, no creds, egress to package registries only"
image    cliff-dev:0.3.0
workspace mode=rw
home      mode=tmpfs size=512m

egress {
    allow registry-1.docker.io:443
    allow registry.terraform.io:443
    allow pypi.org:443
    allow files.pythonhosted.org:443
    allow dl-cdn.alpinelinux.org:443
}

limits { cpus 2; memory 4g; pids 512 }

This is yolo-dev.tcl — a session in which a developer (or an LLM) can run terraform init and pip install and npm install, but cannot reach the cloud control plane. Egress is opened to package registries only; everything else resolves to 127.0.0.1 and connects to nothing.The DNS trick is the simplest workable enforcement: the session's resolver returns the loopback for any hostname not on the allowlist, and the mitmproxy sidecar drops outbound TCP that wasn't explicitly allowed. Two layers, one purpose: nothing leaves the session that wasn't named in the profile.

An AWS-credentialed profile adds a creds block:

inherit base
describe "Dev image, read-only AWS creds via STS, egress to AWS endpoints"
image    cliff-dev:0.3.0
workspace mode=rw
home      mode=tmpfs size=512m

creds {
    aws helper=aws-sts args={role=READ_ROLE_ARN ttl=3600}
}

egress {
    allow *.amazonaws.com:443
    allow *.s3.amazonaws.com:443
}

limits { cpus 2; memory 4g; pids 512 }

env {
    AWS_SHARED_CREDENTIALS_FILE /run/creds/aws
    AWS_REGION us-east-1
}

The creds block names a helper (aws-sts) and its arguments (a role ARN and a TTL). At session start, the launcher invokes the helper on the host, which assumes the named role via STS and returns short-lived credentials. The credentials are written to a per-session tmpfs and bind-mounted into the container at /run/creds/aws. The container's environment points AWS_SHARED_CREDENTIALS_FILE at that path. Nothing about the long-lived credentials on the host ever enters the container; the container sees only the assumed-role credentials, with the TTL the profile declared.

5.2 Sessions

Every cliff run mints a session. A session is a UUID, a profile name, the resolved profile, a per-session network namespace, a per-session mitmproxy sidecar enforcing the egress allowlist, optionally a credential file mounted at /run/creds, and an audit record. The container exits, the sidecar dies, the tmpfs vanishes, the audit record persists.

cliff sessions lists recent sessions; cliff session <id> shows the detail of one. The session record is the answer to "what did the agent actually do?" — the profile it ran under, the start and end time, the exit code, and the egress events the mitmproxy sidecar logged. It is not a full trace; it is enough to know which profile ran, which endpoints it reached, and whether anything outside the allowlist was attempted.The audit story is deliberately minimal. Cliff is a development environment, not a SIEM. The point of the record is to make it possible to answer "what happened" after a session ends, not to be the system of record for security investigations.

5.3 For LLMs

The launcher exists because LLMs needed it. A coding agent given a shell on the host is given the host: it can terraform apply against production, exfiltrate credentials, install something that breaks an unrelated tool. A coding agent given cliff exec dev-aws-read is given exactly the affordances that profile names — read-only AWS access, egress to AWS endpoints, a writable workspace, and nothing else.

The integration pattern is one paragraph in the project's CLAUDE.md (or its equivalent for other agents):

For any infrastructure command (terraform, kubectl, aws, helm, etc.), invoke via cliff exec <profile> --project=<path> -- <cmd>. Do not run these tools directly on the host. See cliff list for available profiles.

The agent reads that paragraph, sees the available profiles in cliff list, and from then on every infrastructure command runs in a hardened ephemeral session. The host stays clean. The blast radius of a misjudged command is the session's profile, not the user's laptop.

6. Choosing

The image is a shape; the profile is a posture. The two questions are independent:

  1. Which image? Base if you want the substrate and nothing else. Dev if you are writing infrastructure code. Obsv if you are looking at telemetry. Full if you are doing both and don't want to switch tabs.
  2. Which profile? Base for sandbox-only work — read code, run scripts, no network. dev-offline for IaC work without cloud access. yolo-dev when you need package registries but no cloud creds. dev-aws-read or dev-aws-write when you need scoped, time-limited cloud access. obsv-local for telemetry exploration.

7. Deployment scenarios

Where cliff runs is a design decision, not a fact about cliff. The launcher is small enough to live on a laptop, on an EC2 instance, or anywhere else with Docker and a Tcl interpreter. What changes between deployments is who holds long-lived credentials, where the egress proxy sits, and what the trust boundary looks like. Three scenarios cover most of what people actually want.Of the three, only the first ships today. The other two are sketched here because the question of "where does cliff live?" comes up immediately on contact with a non-laptop host, and the answer should not have to be reverse-engineered.

7.1 Laptop only — the current model

Your laptop runs bin/cliff. Long-lived AWS credentials live in ~/.aws/credentials on the laptop, never inside any container. When a profile names creds { aws helper=aws-sts ... }, the launcher calls sts:AssumeRole from the host, gets back temporary credentials with the profile's TTL, and writes them to a per-session tmpfs that's bind-mounted into the container at /run/creds/aws. The container's traffic flows through a per-session mitmproxy sidecar enforcing the egress allowlist. Everything the container does — terraform apply, aws s3 ls, whatever — uses the temporary creds, against AWS endpoints, with the proxy logging it.

Trust boundary: the container. The laptop trusts the container with temp creds for the role's TTL and nothing more. If the container is compromised — if an LLM does something foolish, if a malicious package phones home — the blast radius is the role's permissions for the role's TTL, not the laptop's IAM identity forever.

7.2 Cliff on an EC2 instance, bootstrapped by cloud-init

The laptop launches an EC2 instance — by Terraform run via cliff, by aws ec2 run-instances, however. The instance has user-data that installs Docker, clones the cliff repo, drops profiles in place, and pre-pulls the cliff images. The user SSHes into the instance, and from there cliff run yolo-dev works exactly as it does on a laptop. The instance has an IAM instance role attached, so the AWS profiles use that role's automatically-provided credentials directly — no STS dance needed, because the instance metadata service already provides scoped, rotating credentials.EC2 instance metadata at http://169.254.169.254/ serves credentials for whatever role is attached to the instance. AWS rotates them automatically. The AWS SDK picks them up by default. Cliff's aws-sts helper is for the laptop case where there is no instance metadata; on EC2 the helper would degenerate into "read what the SDK would have read anyway."

What this scenario buys you: cliff's egress, tmpfs home, audit log, and resource caps, in a place where you wanted a hardened shell anyway. What it costs: a slow first boot, a non-trivial cloud-init, and the operational story of "what version of cliff is on this instance" is whatever the user-data pulled. A pre-baked AMI is the obvious next step if this becomes routine.

7.3 EC2 with an instance role, no cliff on the instance

The instance has a role attached. The user SSHes in and runs aws and terraform directly. There is no cliff on the EC2 host; the instance role is the leash. This is the scenario where you decide cliff's other features — egress allowlist, ephemeral home, audit — are not worth the operational tax on every dev box, and that the IAM role boundary is sufficient.

This is the right answer when "give me a hardened sandbox" is not the actual requirement — when the actual requirement is "give me an EC2 box where I can do AWS work, scoped to a role." Adding cliff on top would be belt-and-suspenders for a problem the role already solves. What you give up is the parts of cliff that have nothing to do with credentials: the egress allowlist (the box can talk to anything the security group allows), the audit log (whatever shell history you keep is your record), and the ephemeral home (the box is long-lived, with whatever state accumulates).
